Key technical concepts to know
Why Flutter?
Single codebase for Android (and potentially iOS). Dart compiles to native ARM code — near-native performance. Rich widget library for maps and multilingual UI. Fishermen use Android — Flutter Android was the right choice.
Why Firebase Realtime DB?
Real-time boat location tracking needs instant sync across devices — Firebase Realtime DB pushes updates to all connected clients instantly. If Boat A reports a good zone, Boat B sees it in milliseconds. SQL databases don't do this natively.
Crowd-aware algorithm
Count active boats in each zone using real-time Firebase data. If zone A has more than threshold T boats, reduce its recommendation score. Recommend zone B instead. Prevents overfishing and overcrowding — like traffic routing for the sea.
Ocean data for predictions
Fish concentrate where sea surface temperature (SST) is optimal for their species and chlorophyll is high (indicates plankton = food). Satellite APIs (NOAA, INCOIS) provide this data. We map it to GPS zones and score each zone.

Why Flutter? Why not native Android or React Native? Easy
vs Native Android (Java/Kotlin): Native gives best performance but requires maintaining separate iOS codebase if we ever expand. Flutter gives near-native performance with a single codebase.

vs React Native: React Native uses a JavaScript bridge to communicate with native components — introduces latency. Flutter compiles directly to native ARM code — faster, especially for map rendering which is performance-intensive.

Why Flutter specifically: Rich widget library, excellent Google Maps integration, strong multilingual/localization support for Kannada, active community. For a fishing community app on Android, Flutter was the most productive and performant choice.
Why Firebase Realtime Database and not Firestore or MySQL? Medium
Firebase Realtime DB vs Firestore: Realtime DB is optimized for low-latency sync of simple data — like GPS coordinates updating every few seconds. Firestore is better for complex queries on structured data. For live boat tracking, Realtime DB's websocket-based push model is ideal — updates reach all connected clients in milliseconds without polling.

vs MySQL: MySQL is a relational database — requires polling (client asks "any updates?" repeatedly) which is inefficient and slow for real-time location tracking. Firebase pushes updates to clients automatically.

Key insight: "For the crowd-aware system to work, we need to know in real-time how many boats are in each zone. Firebase Realtime DB gives us this instantly — when a boat moves, all other app instances update automatically."
Explain the crowd-aware recommendation algorithm in detail. Medium — core feature
Step 1 — Zone definition: The sea is divided into GPS grid zones (e.g. 1km × 1km cells).

Step 2 — Real-time boat tracking: Each active app user shares their GPS location. Firebase stores this — we count how many boats are in each zone in real-time.

Step 3 — Base zone scoring: Each zone gets a base score from satellite data — higher sea surface temperature suitability + higher chlorophyll = higher base score.

Step 4 — Crowd penalty: If zone has more than threshold T boats (say 10), we apply a penalty to its score. The more boats, the higher the penalty.

Step 5 — Final recommendation: App shows top 3 zones by final score = base score minus crowd penalty.

Real-world analogy: "It's exactly like Google Maps routing — it doesn't just show the shortest path, it avoids congested roads. MatsyaMitra doesn't just show where fish are, it avoids overcrowded zones."
What ocean data do you use and where does it come from? Medium
Sea Surface Temperature (SST): Different fish species thrive in specific temperature ranges. For example, Indian mackerel prefer 26–29°C. SST data from NOAA (National Oceanic and Atmospheric Administration) satellites or INCOIS (Indian National Centre for Ocean Information Services) — India's own ocean data platform.

Chlorophyll concentration: High chlorophyll = high phytoplankton = high zooplankton = more fish. This data is also available from satellite remote sensing via NOAA or NASA's MODIS satellite.

How we use it: We fetch this data via APIs, map it to our GPS grid zones, and compute a fish probability score per zone. Combined with crowd data — final recommendation is generated.

Honest note for interview: "We're currently using publicly available datasets from INCOIS for our prototype. In production, we'd integrate real-time satellite API feeds with daily updates."
What are the challenges of building for fishermen as users? How did you address them? L3 — UX thinking
Challenge 1 — Literacy and language: Many fishermen may not be comfortable reading English or even Kannada text fluently.
Solution: Multilingual support (Kannada first), large UI elements, map-centric design (visual zones not text), voice alerts for safety warnings.

Challenge 2 — Connectivity at sea: Deep sea has poor or no mobile network. The app must work offline or with minimal data.
Solution: Pre-download zone data when in port with good connectivity. Cache the last known recommendations and maps locally using Flutter's local storage. Send only lightweight GPS coordinates (few bytes) for location tracking — not heavy data.

Challenge 3 — Device quality: Fishermen may use low-end Android phones. The app must perform on 2GB RAM devices.
Solution: Lightweight Flutter build, optimize map tile loading, avoid heavy animations.

Challenge 4 — Trust: Fishermen rely on generational knowledge. An app recommendation contradicting traditional wisdom may be ignored.
Solution: Show WHY a zone is recommended — "High fish probability: warm water + low crowd." Transparency builds trust.

What is the difference between real-time and batch processing? Which does MatsyaMitra use and why? L3
Batch processing: Data is collected and processed at scheduled intervals. Example: satellite data is processed once daily to compute zone scores. Low cost, high throughput, slight delay acceptable.

Real-time processing: Data is processed as it arrives. Example: boat GPS locations are updated and reflected instantly — crowd counts change in real-time.

MatsyaMitra uses BOTH:
- Satellite data (SST, chlorophyll) → Batch processing daily. Satellite data updates once per day anyway — no point in real-time processing.
- Boat location + crowd counting → Real-time via Firebase. Boats move constantly — crowd data must be current.

Key insight: "Choosing the right processing model for each data type is an architectural decision. Applying real-time processing to satellite data would be expensive and wasteful. Applying batch processing to GPS tracking would make the crowd-aware system useless."
What happens if a fisherman's phone dies at sea? Does MatsyaMitra handle this? L3 edge cases
Great edge case — shows L3 systems thinking.

Problem: If phone dies, Firebase still shows the boat's last location — it appears "active" in a zone, inflating crowd count incorrectly.

Solution — TTL (Time To Live) on location records: Each location update includes a timestamp. If no update received from a boat UID within 30 minutes, consider the boat "offline" and remove it from crowd count calculations. Firebase Cloud Functions can run this cleanup automatically.

Additional solution: Boats report "going offline" when entering port — triggering removal from active tracking. This also helps with safety — if a boat goes silent unexpectedly, it could trigger a safety alert to coast guard integration (future feature).

Why this answer is L3: You thought about failure modes, not just happy paths. Real engineers think about what happens when things go wrong.
Compare MatsyaMitra's architecture to Costra's. What's different and why? L3 cross-project
Costra: Web app — React + FastAPI + MySQL + Firebase Auth. Stateless REST API backend. Users are tech-savvy businesses. Data is structured, relational. No real-time requirements.

MatsyaMitra: Mobile app — Flutter + Firebase Realtime DB. No dedicated backend server — Firebase handles real-time sync directly. Users are fishermen with low-end devices and poor connectivity. Data is geospatial + real-time. Offline capability is critical.

Key architectural difference: Costra follows a traditional 3-tier web architecture with a dedicated application server. MatsyaMitra uses a Backend-as-a-Service (BaaS) model — Firebase IS the backend for real-time features. This was a deliberate choice — a dedicated server would add latency and complexity for real-time GPS tracking that Firebase handles natively.

What this shows: "I don't use the same architecture for every project. I choose the right tool for the problem — Costra needed relational data + complex business logic so FastAPI + MySQL was right. MatsyaMitra needed real-time geospatial sync so Firebase BaaS was right."
